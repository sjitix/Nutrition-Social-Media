The rule that outranks the layers: the model decides, the engine computes. L4 may ask L3 for anything; it may never do arithmetic itself, and it is never the thing that claims a change happened. Any refactor that puts a number in L4 is wrong however tidy the folders look.

Tooling is deliberately exempt. scripts/ may reach inside any module, because a suite that can only see the public surface can only test the public surface.
The big one

recipeDb.ts is three jobs sharing a file

10,850 lines, 24 exports, 19 direct consumers — including UI pages, which is how the whole library reaches the browser.

71% · the 501 recipe seeds
11%
18% · executor

Lines 179–7863 are data · 7864–9010 selection, rebalancing and batch · 9011–10850 the executor and its note-writers.

Split over two days, data first, each behind a barrel that re-exports today's eighteen consumed names unchanged — so no importer is touched on either day. The gate is that test:engine produces the same number of passes before and after: a split that changes behaviour shows up as a count change, and one that loses an export fails tsc.

The contracts that carry the most weight

plan/execute

“The only code allowed to change a plan, and to say that it changed.”

PublicapplyOperations(profile, plan, operations, previous?)
Privateevery per-tool handler, reimposeLocks, guaranteeFridge, guaranteeBoost, findRecipeForSwap, the note-writers, the undo snapshot
InvariantsNever mutates what it is handed. A refusal is reported, never faked. replyOverride on a crisis discards the model's words entirely. planChanged is a deep comparison of before and after — never a guess from which tool ran.

assistant/primitives — the biggest sealing win

“The vocabulary a model may emit, and the executor that runs it.”

PublicPrimitiveOp · applyPrimitives · memoryContext · AssistantTurnV2Schema · expandConstrain · applyRemember
Seal22 names — ConstrainOp, SwapOp, LogOp and the other 15 per-op interfaces, plus verbToOperation and PrimitiveOpSchema. None is imported anywhere. They are the shape of the implementation, published as API.
InvariantEvery write reaches the engine through applyOperations. This module adds no arithmetic of its own.

assistant/loop

“Call the model, execute what it asked for, feed the result back, call again, stop.”

PublicrunAgent · ModelFn · TranscriptEntry · AgentTurn · MAX_STEPS
InvariantsThe model is injected as a ModelFn — the line that makes the loop testable with no model at all. MAX_STEPS = 8 is a cap, not a target; hitting it sets gaveUp and the user is told. One undo snapshot per user turn, taken before the first write.

persistence/storage

“The only place that knows a localStorage key name.”

Publicthe load/save pairs, and clearAll
PrivateKEYS, and the JSON encoding
InvariantOne concept, one key, and no other module may name one. A second saved-recipes key was added once and the two lists drifted apart silently until an audit found it. The gate enforces this.

nutrition/exclusions

“Allergen and diet matching, word-aware, in both directions.”

PublichaystackBlocked · parseExclusionTokens · dietTagConflicts · wordMatches
InvariantI2 — an allergen never reaches a plate. Matching is word-aware in both directions: peanuts must match peanut butter, and egg must not match eggplant. Every matcher in this module gets the same fix — the sibling-path miss has cost three separate incidents.

The trap this refactor must not walk into

A barrel is a bundler black hole. If the plan barrel re-exports both selectWeekFromDb and RECIPES, any client component importing one small helper may pull all 501 recipes into the browser. That is not hypothetical — it is the Explore payload bug we already have.

plan (server barrel)

The engine, the seeds, the executor. Imported by API routes, server components and tooling.

plan/cards (client-safe)

A RecipeCard projection — only the fields a card renders. The only one a client component may import.

weekStats.ts already proves the pattern: it imports only a type, which is why one route is 105 kB while Explore is 187 kB.

Day 1

Making it enforceable: check:boundaries

An unenforced boundary is a comment. A homemade gate in the family of check:recipes — no new dependency — asserting six things:

#RuleWhy it exists
1No module imports above its layerthe layering is otherwise a comment
2Only a module's barrel may be imported from outside it — no deep pathsthis is what makes “private” real
3Only persistence/storage may contain a localStorage key stringa second saved-recipes key already drifted once
4No client component imports a server barrelthe 185 kB Explore payload, made impossible
5No import cyclestrue today — this keeps it true
6No emoji in src/a standing project rule with no enforcement today

Every failure prints the offending file, the import, and the rule in plain English. A gate that says “violation in 3 files” teaches nobody anything.

How we get there

Three phases, in this order

1

Seal, without moving anything

An index.ts per module; move the unconsumed names off the public surface; delete runAssistant, which has no caller anywhere. No call site changes. Low risk, do it first.

2

Split recipeDb

Two days, data first, each behind a barrel. The gate is an identical test:engine count.

3

Move the folders

Mechanical, one commit, tsc as the gate. Be honest about the value split: phases 1 and 2 deliver nearly all of it. Phase 3 is navigation, worth doing only because it is cheap — and it must never share a commit with a behaviour change.
