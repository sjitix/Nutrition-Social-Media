# D5 — ingredient identity: the design, before the code

*V1 milestone A5. Written 2026-10-03, before any code, because it changes a data shape that every
nutrition lookup in the app depends on. Read with `01-dimensions-and-milestones.md` D5 and §8.*

## What is true today (measured from the engine, not estimated)

- **501 recipes carry 2,296 ingredient references**, naming **179 distinct** ingredients.
- They resolve against **180 curated ingredients** (`scripts/ingredient-map.json` → generated
  `nutrientTable.generated.ts` and `unitGrams.generated.ts`). One curated entry is used by no recipe.
- **Every lookup is by free text:** `name.trim().toLowerCase()` is the key into `NUTRIENT_TABLE` and
  `UNIT_GRAMS.perIngredient`. Seven sites do it: `deriveMacros` (plan/library), `microsForIngredients`
  (nutrients), `gramsFor` (units), two in plan/report (substitutions), and the `check:recipes`,
  `export:recipes` and test-engine scripts.
- **103 of the 2,296 references resolve only after case/whitespace normalisation** ("Greek yogurt" vs
  "greek yogurt"). Nothing checks this at compile time; `check:recipes` catches a miss only when run,
  and since today (D5b's finding) nothing runs it automatically.

## Why identity, and why now

1. **Growth.** The owner wants 400 ingredients / 900 recipes. Every new recipe written by hand is
   another chance to type a name that silently resolves to nothing (and `deriveMacros` then *skips*
   it — D5b fixes that half).
2. **Real products.** A Lidl-style product, a price, a store's availability can only attach to a thing
   with a stable identity. A display name is not one: the day "greek yogurt" is renamed "Greek
   yoghurt" every attachment breaks.
3. **Renames become free.** An id lets a display name change without touching a single recipe.

## The design

### 1 · Every curated ingredient gets a `slug` — its permanent id

- Kebab-case, ASCII, derived ONCE from today's map key: `"brown rice"` → `brown-rice`, `"greek
  yogurt"` → `greek-yogurt`. Stored **explicitly** in `ingredient-map.json` as `"slug"`, so it never
  changes when the name does. **Not `id`:** that field already means "pin this USDA fdc_id" in the map.
- `build:nutrients` emits `src/lib/data/ingredients.generated.ts`: `INGREDIENT_SLUGS` (`as const`), the
  type `IngredientSlug` (a union of all 180), and `INGREDIENTS: Record<IngredientSlug, { name, fdcId }>`.
  The nutrient and unit tables key by slug from then on.

### 2 · Recipes carry the slug; the type system does the checking

- A seed ingredient becomes `{ slug: IngredientSlug; name: string; quantity: string }`. `name` stays
  for DISPLAY (it may keep its casing), `slug` is what every lookup uses.
- Because `IngredientSlug` is a union of the 180 real slugs, **`tsc` rejects a typo at compile time** —
  the strongest possible form of "every reference resolves". `check:ingredients` adds what types
  cannot: no curated entry without an FDC id, no two slugs for one FDC food unless intended, every
  slug used or deliberately unused.
- The rewrite of `src/lib/data/seeds.ts` (2,296 references) is **generated by a script with asserted
  anchors** that resolves each name through today's exact rule, and fails on anything ambiguous.

### 3 · Lookups go through one resolver

- `resolveIngredient(nameOrSlug)` → `IngredientSlug | null`, in `src/lib/data/` (L1). Engine code with
  a library recipe uses the slug directly; meals that did NOT come from the library — an imported
  recipe, a logged "burger and chips" — still only have a name, so the resolver keeps today's
  `trim().toLowerCase()` rule as the fallback **for those only**.
- `Meal.ingredients[]` gains an **optional** `slug` (the zod schema change is additive, so stored plans
  and the accounts lane's synced data stay valid). `recipeToMeal` copies it through.
- All seven lookup sites switch to `resolveIngredient`, so there is exactly one rule for "which
  ingredient is this".

## How it is proven

The same discipline as D2/D3: a fingerprint of the engine before and after must be identical **except
for the new `slug` field** (stripped before hashing), plus `check:recipes`, `check:boundaries`, `tsc`
and `test:engine` as the ship gate. The order is chosen so each step is independently green:

1. map gets slugs → generator emits `ingredients.generated.ts` (no consumer yet) — nothing changes
2. `resolveIngredient` + `check:ingredients` (reads today's names) — nothing changes
3. seeds rewritten to carry `slug` (generated) + the seed type requires it — data shape changes,
   behaviour does not (fingerprint)
4. lookup sites switch to the resolver, tables key by slug — behaviour must not change (fingerprint)
5. `Meal.ingredients[].slug` (optional) flows through `recipeToMeal`

## Progress

- **Steps 1–2 done 2026-10-03.** All 180 curated ingredients carry an explicit `slug` in
  `ingredient-map.json` (derived once, all unique, the JSON round-tripped byte for byte so the diff is
  only the new field); `build:nutrients` emits `src/lib/data/ingredients.generated.ts`
  (`INGREDIENT_SLUGS`, the `IngredientSlug` union, `INGREDIENTS`), and the two existing generated
  tables came out unchanged; `src/lib/data/ingredients.ts` holds `resolveIngredient`; and
  **`npm run check:ingredients`** passes: 2,296 references, 179 distinct, all resolving.
- **What it reports (not failures — curation decisions for after D5):** one curated ingredient is
  unused (`beetroot`); and several slugs share one USDA food. Some of those are deliberate
  approximations (sriracha / harissa / buffalo sauce in tsp amounts), but some are the same thing
  named twice — `egg` / `eggs`, `bell-pepper` / `bell-peppers`, `soy-ginger-sauce` /
  `ginger-soy-sauce` — which identity should eventually merge into one slug with aliases.
- **Step 3 done 2026-10-03 (shipping next).** All **2,296** references in `data/seeds.ts` carry their
  slug — `{ slug: "greek-yogurt", name: "Greek yogurt", quantity: "200 g" }` — inserted by a script
  that asserted the count, resolved every name through `resolveIngredient`, and proved the slug fields
  were the ONLY change. The recipe ingredient type now REQUIRES `slug: IngredientSlug`; a probe with
  `"brown-rise"` failed `tsc` with "Did you mean 'brown-rice'?". A slug-blind 105-point fingerprint
  is identical before and after, and `check:ingredients` / `check:recipes` / `check:boundaries` pass.
- **Step 4, refined before building it:** the lookups go through the resolver, but the generated tables
  stay keyed by the curated NAME — the resolver maps slug → name → table. Re-keying the tables by slug
  would rewrite every script that indexes them (`check-recipes`, `export-recipes`, the test suite) for
  no behavioural gain; the identity guarantee is the same either way, because the one place that
  decides "which ingredient is this" is the resolver. The table key becomes an internal detail.

## Decided, and why

- **A separate slug, not "the lowercase name is the id".** Making the canonical name the id would have
  been less work, but it ties identity to spelling — the exact thing that breaks when a product or a
  translation is attached later.
- **Optional on `Meal`, required on seeds.** A seed is ours and must be exact; a meal can come from
  outside (import, log) and must keep working without one.

## Not in D5

- **Retail products** (the Lidl layer) — attaches to slugs, straight after V1 (owner decision #6).
- **New ingredients** — the expansion waits for D5b (the maths proven) and the B7 curation helper.
