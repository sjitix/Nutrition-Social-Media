# Afternoon — the adversarial review, and what it changed

**Milestone:** harden A1–A4 before any key exists. **Solved:** done — every finding fixed, tested,
mutation-checked and shipped.

## What moved

- **A five-lens review ran as a workflow:** data loss, security, the real Supabase API (checked
  against Supabase's own source and docs), React/UI, and integration with the rest of the app, with
  each finding sent to two skeptics told to refute it. It found ~40 findings; after merging duplicates,
  the real ones were:
  - **login CSRF** — the page accepted session tokens from its own URL, so anyone could sign a browser
    into *their* account and receive its profile → **PKCE** sign-in;
  - **cross-account upload** — signing in as B on a browser holding A's data pushed it into B's
    account, and a mirror in another tab followed whatever session was stored → an **owner** record,
    the account-switch guard, and each sync **pinned** to its account plus a cross-tab listener;
  - **jsonb reorders keys** → every sync saw untouched stores as changed and took a backup →
    key-order-blind comparison;
  - **"Put it back" wrote deletions** for every store the copy lacked, and sync spread them to every
    device → restore writes only what the copy holds and *forgets* the rest locally;
  - **unchanged re-saves counted as edits** (screens re-save what they loaded) → a no-op;
  - **stale writes won on the server** (an offline phone overwrote a newer week) → `upsert_state`,
    migration 0002: a store only moves forward in time;
  - **a failed first sync was never retried, and the tab pushed on top of data it never pulled** → the
    mirror stays paused until a full sync succeeds; retries on focus, online and the next call;
  - smaller: sign-out signed out every device (`scope=local`), the setup guide lacked the SMTP step
    without which only the owner's organisation can receive emails, one refused store blocked all the
    others, routine pulls evicted real backups (now only unsynced edits are backed up, three kept), the
    privacy note overclaimed twice, the iPhone download link died after one second, focus and
    announcements for keyboard and screen-reader users.
- **The account suite grew 94 → 238 checks**, including the real `client.ts` end to end against an
  in-memory Supabase that applies RLS, PKCE, conditional writes and jsonb key order. **Eight
  mutations** — one per new guard — each turn it red (`node scripts/mutate-account.mjs`).
- **`storage.ts` now owns the theme key**, so the v1 lane can pay ThemeSwitch's boundaries debt.

## What got in the way

- **My own fakes were the reason the bugs were invisible** (lesson 52): a server that kept key order
  and accepted every write could not show either failure. Fixed by making the fakes do what Postgres does.
- **Three of eight new tests could not fail** (lesson 53) — found only by removing each guard and
  running the suite. Each was rewritten to create the condition only its guard stops.
- **Shell quoting corrupted edits twice** (lesson 35 again): a regex's escapes became literal broken
  characters, and backticks in a `node -e` string were run as commands. Both caught by checking the

- **Working beside a live review:** editing files the reviewers were reading would have moved the code
  under them, so the fixes were built in a second, temporary worktree (`../NutriFlow-accounts-wip`)
  and shipped from there.
- **A busy machine:** with three lanes and a dozen review agents running, `tsc` took over five minutes once.

## Decided, with the reason

- **No "upload this browser's data?" prompt on first sign-in.** A reviewer suggested one. With PKCE a

- **The tab reloads once when a pull brings the week or profile** — a stopgap until the assistant
  screen and the undo snapshot re-read on their own (asked of the v1 lane). Bounded to once per 30 s

# Later: the SQL, executed for the first time

**Milestone:** close the one gap the review left, which was that the migrations had never run.
**Solved:** done. They now run in real Postgres from one command, and the first run found a real gap.

## What moved

- **`node scripts/test-account-sql.mjs`** runs both migrations, each applied twice to prove they are
  idempotent, and then the README's RLS plan. It runs them in **PGlite**, the Postgres engine compiled
  to WebAssembly.
  - Supabase's own pieces are stubbed the way Supabase defines them: the two API roles, `auth.users`,
    `auth.uid()` from the JWT claims, and, after the first run, **Supabase's default grants**.
  - 37 checks. `--mutate` removes fifteen guards in turn (each policy, each revoke, the cascade, the
    size limit, the forward-only rule), and every removal turns a check red.
  - PGlite installs itself once into the OS temp folder, so neither lane's `package.json` changes.
- **TRUNCATE revoked from signed-in users (0001).** Under Supabase's defaults, `authenticated` held ALL
  on the table: the migration granted the four verbs and never revoked the rest. TRUNCATE ignores RLS.
  The check had user B run it, and the table went to zero rows for every account. The REST API has no
  TRUNCATE, so this was unreachable from a browser, but it is closed in the schema anyway.
- **The README's test plan gained rows 5, 5b and 5c:** update and delete with no `where`, and truncate.
- **The store-size cap counts bytes, as the server does** (`storeBytes` in `sync.ts`). It counted
  `.length`, which is UTF-16 units. Measured in PGlite, a chat's stored jsonb is within 3% of its
  UTF-8 size in any script, but 2.9× its `.length` in Japanese and 1.8× in Arabic. So a long
  non-Latin chat passed the client's check, was refused by the server, and, because an edit retries a
  held store, was uploaded again on every message. Now it is held locally and named "too large".
  One test, and a ninth mutation that puts `.length` back.

## What got in the way

- **The first run passed everything,** because the stub granted nothing by default, so "anon gets
  nothing" could not fail. Only once the stub had Supabase's real defaults could the check fail, and
  it then did (lesson 56).
- **One of my RLS tests was vacuous.** "B updates A's row where user_id = A → 0 rows" stays at 0 even
  with the UPDATE policy deleted, because a WHERE that reads a column brings the SELECT policy in. All
  four combinations were measured before this was written down. The README's row 5 had the same flaw
  and would have misled the live run.
- **`db.query` runs one statement** (the extended protocol), so a migration file needs `db.exec`. On
  the first attempt every check reported "relation does not exist", because no migration had applied.

# Then: clocks, which lost edits silently

**Milestone:** settle the question the second review was asked, whether device clock skew is safe.
**Solved:** it was not, and it is fixed and shipped.

## What moved

- **Reproduced before anything was changed,** against the frozen snapshot's real engine, with a server
  applying `upsert_state`'s forward-only rule:
  - a phone 2 h slow edited AFTER syncing, and its next sync pulled the old week back over the edit,
    with **no backup**;
  - after a device a day fast wrote once, a correct phone's later edit never reached the account and
    was reverted;
  - a merged store against the fast device re-sent on every sync and never settled.
  A later search for raw clock reads found a fourth: "Put it back" stamped `Date.now()` itself, so on
  a slow device the restored copy was pulled back over, after its backup had been discarded.
- **The fix is one pure rule, `nextStamp(now, prev)` in `merge.ts`:** a write is stamped now, or just
  after the value it replaces if that is later (a logical clock). It is used by `write()`,
  `restoreBackup`, `importedAt` and merges. A union that this device holds under an older stamp is
  now written to both sides, stamped past both, instead of being pushed under its old stamp, which
  the server would skip forever. Raw clocks now decide only true conflicts, where the backup applies.
- **Tests (252 now):**
  - the rule itself, and merges stamped past both copies;
  - the engine against a device a day fast: the union lands, and the next sync does nothing;
  - end to end through the real `storage.ts` and `client.ts`, with `Date.now` skewed per device: a
    2-h-slow phone keeps its edit through the next full sync, and a correct device's edit lands
    after a day-fast device wrote;
  - the write path, restore and `importedAt` each stamp past a value from a clock running ahead.
  **Five new mutations**, one per guard, all caught (14/14).

## What got in the way

- **The design comment had already accepted the risk, in the wrong size:** skew "can mis-order two
  edits made within seconds". The real failure took hours of skew, which is ordinary after a dual
  boot, and it was silent. The rule-5 backup that was meant to catch it compared the edit against the
  last agreement using the same skewed clock, so it never fired.
- **The ship of the size fix stopped twice** on CONTEXT edits from other lanes: once before the gate,
  and once after a 30-minute gate, with the commit intact and unpushed. Both were merged by
  verifying that every block but this lane's was byte-identical to `origin/main`.

# Evening: batch 4 — the write fence, late answers, validation, accessibility

**Milestone:** the rest of the second review's findings. **Solved:** all of them, plus four gaps that
batch 4's own mutation run and a re-read of the change exposed. Shipping; batch 5 is built beside it.

## What moved

- **THE WRITE FENCE (`storage.ts`).** Each browser's data has a generation (`nutriflow.epoch`), begun
  anew whenever the browser changes hands: the account-switch guard, or "Delete everything in this
  browser". A tab pins the generation at its first read of any key, and a tab whose generation is no
  longer the browser's can write nothing: no store, no write time or sync marker, no owner, no copy.
  `takeBackup` throws, so `putBackCopy` and an import refuse with a sentence before they change
  anything. The same key is the reload signal, so "Delete everything" in one tab now reloads the
  others with accounts switched off too.
- **Late answers after a stop change nothing.** A push or pull answered after "Delete everything", a
  sign-out or a switch writes no bookkeeping; a re-sync that was waiting behind a push does not start
  in a stopped tab; a skipped push gets a bounded follow-up pull instead of "saved" over a store the
  account holds differently.
- **A token renewal cannot revive a session** that was signed out or replaced meanwhile (`liveSession`).
- **The sentence survives the reload.** What a sync said ("set aside", "your account had newer data")
  is carried across the reload `<AccountSync/>` does for it.
- **`validate.ts` checks every optional field the screens read**, so a crafted file or account row
  can no longer pass validation and then crash Week, the meal sheet or Today.
- **Accessibility, both account surfaces:** one live region that is always in the page, labelled
  confirms, and focus that never falls to the page body after an action removes the control that had it.
- **Privacy:** the note says what is logged (each sign-in and its hourly renewal, with email and IP)
  and for how long, and `supabase/README.md` gains the step that makes that true: turn off "Write audit
  logs to the database", or the entries stay in the project database for good. Path and retention
  checked against Supabase's docs (1 day on Free, 7 on Pro, 28 on Team, 90 on Enterprise).
- **`savedStore` is tested** at last: saving twice keeps a recipe saved, removing an unsaved one changes
  nothing (both run through a toggle), non-names in storage are not shown, and `kind` says "account"
  only when signed in. The `useSaved` hook still has no test: this repo has no React renderer.

## What got in the way

- **Three mutations survived, and each was a map to a gap (lesson 63).**
  - The re-sync guard looked tested, but `signOut` waits for the push before it stops anything, so the
    guarded order never happened in the test. Only a stop that does not wait reaches it (another tab
    signing out, "Delete everything", a switch), and the test now uses one.
  - Asking why the `markSynced` and `restoreBackup` fences went uncaught found two writes the fence
    did not cover at all. `putBackCopy` took its safety copy BEFORE the fenced restore, so in a stale
    tab it could push the previous person's set-aside copy out of the three kept, then restore nothing.
    And a stale tab's sync, answered late, recorded the PREVIOUS account as the browser's owner: the
    next time that person signed in here, the new person's data would have been uploaded into their
    account. Both are fenced now. A "deaf" tab in the tabs suite, whose storage events wait while its
    sync's answer lands, proves it, and every stale act is checked to leave the whole storage
    byte-identical.
- **The fence learned its generation only from store reads,** so a tab that had only listed the copies
  adopted the new generation at its first write. It now pins at the first read of any key.
- **That move put the pin outside `readKey`'s `try`.** In a browser where storage access throws
  (Safari with site data blocked), every load threw and the screens would have crashed. Found by
  re-reading the change, reproduced, fixed, and given a test and a mutation.
- **Two old mutations had gone stale** when their code was rewritten: one duplicated a newer mutation
  and was removed, one was re-anchored. The runner gained `--only`, so one guard re-checks in seconds.
- **`git stash` would have been a trap.** The stash stack is shared by every worktree of the repo, and
  another lane's stash was already in it, so a stash here would have been the next `git stash pop`
  anywhere. Fast-forwards were done by copying the work aside instead.
- **The adversarial review of batch 4 ran out of usage** before any lens reported (four finders, 1.2 M
  tokens, nothing returned). Batch 4 ships on its gate, and the review re-runs against `main`.

# Night: batch 5 — an account deleted on another device, and links as GoTrue issues them

**Milestone:** the last of review 2's platform findings (platform-4 d), the fake's two remaining
gaps, and one claim of this lane's own that the platform does not bear out. **Solved:** all three.

## What moved

- **A device whose account was deleted elsewhere now says so.** Its token stays valid at PostgREST
  until it expires (a JWT is stateless), so its next pull reads an empty account and its push breaks
  `user_state`'s foreign key to `auth.users`. Postgres raises 23503, PostgREST sends 409, and the
  client read that as an ordinary refusal: "couldn't store your week and your profile… everything else
  is synced" for up to an hour, then "your sign-in expired". A 409 carrying 23503 is now its own error
  kind, `gone`: the device stops syncing, forgets the sign-in (only if it is still that account's), and
  says the account was deleted. The data stays, still marked as the deleted account's, so the next
  sign-in sets it aside, as on the device that deleted it.
- **Proven at both ends.** In real Postgres (PGlite), `test-account-sql.mjs` deletes an account and
  then writes with its still-valid token: 23503. A new mutation drops the foreign key, and three checks
  go red. In the client, the fake answers a deleted account as PostgREST does (reads `[]`, writes 409),
