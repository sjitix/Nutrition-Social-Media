# 2026-10-23 (accounts lane) — "Try again" ships, after a fourth review and a fifth look

**Milestone:** the local live run of accounts: "Try again" after a failed sign-in exchange, run against
the real GoTrue.
**Solved:** done. The batch landed as `4fa187f`, with the docs in the commit after it. What it fixes, and
its first three reviews, are in [`2026-10-22-accounts.md`](2026-10-22-accounts.md).

## What moved

- **The fourth review** (3 reviewers) found that this batch's own fix from the third review had opened
  four holes. That fix paired a kept code with the verifier it was exchanged with, so a kept sign-in now
  finished where before it could only be refused. The session ended before the review's verifiers ran,
  so every finding was checked here by hand.
  - **Keep or drop was decided by the wrong request.** `sendSignInLink` gave up the kept sign-in by
    comparing the new address with the browser's pending request, which another tab can replace. So a
    tab could offer "Finish the earlier sign-in" for an address it had moved away from, or drop one it
    was repeating. The kept sign-in now records its address, and the decision is made on it.
  - **"Delete everything in this browser" left a working sign-in behind.** The kept code and verifier
    stayed in the tab's sessionStorage. Now:
    - `clearAll` drops this tab's;
    - the kept sign-in is stamped with the browser's data generation (THE WRITE FENCE), so another
      tab's is stale at once, and that tab drops it when it hears;
    - the account page mounts a fresh sign-in panel after the clear.
  - **A null from `retrySignIn` read as success.** The panel said "Signed in" while the browser was
    signed out. `retrySignIn` now throws a sentence when there is nothing to finish, and offers nothing
    once the browser is signed in.
  - **A newer link after "Try again" finished** landed with the "no request held here" sentence, every
    cause of which was false.

  Also, two comments overstated what a different letter case did. And the fake deleted a code already
  presented when a newer request was accepted. GoTrue keeps it (`magic_link.go` creates a flow state and
  touches no other), and so does the fake now.
- **A fifth look** (one reviewer, on the fourth round's diff) found four more, each now covered by a
  check:
  - **A sign-in still finishing when the browser was cleared** saved its session, or its code for "Try
    again", into the emptied browser. The exchange now reads the generation before it waits and keeps
    nothing if it changed.
  - **A sign-in in another tab only hid a kept sign-in,** so a sign-out there brought it back, and "Try
    again" signed the person in again. It is now dropped: by a tab that hears the sign-in, and by one
    that reads it while signed in.
  - **The "already signed in" sentence said the link "isn't needed"**, which is false for a link asked
    for on another device and opened here, a common case. It now says this browser has no sign-in
    waiting for it, and to ask again on the other device.
  - **After "already signed in", the panel kept its signed-out view** and offered the email form. It now
    takes that sign-in up.
- **Every new guard was shown to fail the check written for it**, not an unrelated one. Eleven new
  mutations bring `mutate-account.mjs` to 114. The fake suites pass 354 + 48.
